# Registry Review — `data/law/` ↔ Qdrant `la8159_law`

## Executive summary

The corpus is **not in a consistent state** (`validation_ok: false`). The headline number — 26 articles "missing in Qdrant" — is small relative to 1,145 total, but **all 26 are Chilean-law articles**, which signals a systematic ingestion gap rather than random loss. Separately, the registry surfaces a large but non-blocking set of *identity* issues (293 colliding ELIs, 294 alias-only articles) driven almost entirely by the PT/EN duplication of international treaties, and a **52-item content-drift set** that needs a canonical-source decision before you can trust retrieval results for legal QA.

Below I break the findings into blocking, should-fix, and informational.

---

## 1. Blocking issues

### 1.1 The 26 genuinely missing articles are a Chilean cluster
Every missing ELI is `CL.*`:

| Cluster | Source file(s) | Missing ELIs |
|---|---|---|
| Prevaricación | `CL/CodigoPenal_Prevaricacion.md` | Art.223 – 232 (10) |
| Individual CP articles | `CL/CL.CPCL.C1.Art.228/229/256/257/269_bis.md` | 5 |
| LPDC / SERNAC | `CL/CL.L19496.Art.*.md` (11 files) | 53A, 56, 56A–56H, 57 |
| L20555 | `CL/CL.L20555.Art.1.md` | 1 |
| Constitución | `CL/Constitucion.md` | `Art.19.2` |

The fact that **all 11 standalone `CL.L19496.Art.*` files are 0/1** strongly suggests these files were created *after* the last Qdrant ingestion run and were never synced. Same pattern for `CodigoPenal_Prevaricacion.md` (10 articles, 0 ingested).

**Note on `Art.269_ter`:** the standalone `CL/CL.CPCL.C1.Art.269_ter.md` reports `articles_in_qdrant: 1` but `source_basename_present_in_qdrant: false`. That means the ELI is present in Qdrant, but it was ingested from a *different* file (`CL/CodigoPenal.md`, which lists the same ELI as alias). Provenance is therefore wrong even though coverage looks fine. Same alias situation applies to `CodigoPenal_269bis_269ter.md`.

**Action:** re-run ingestion scoped to `CL/`, prioritizing `CodigoPenal_Prevaricacion.md` and the `CL/CL.L19496.*` files. Then verify that `source_basename` is written for each ELI so future audits can trace provenance.

### 1.2 Validation flag is misleadingly binary
`validation_ok: false` doesn't tell a downstream consumer *what* failed. Given the registry already contains per-issue counters, consider promoting the flag to a structured status object (e.g. `{blocking: ["missing_eli"], warnings: ["content_drift", "doc_type_drift"]}`) so automated pipelines can gate on the severity they care about. Missing ELIs and doc_type drift are not the same severity.

## 2. Should-fix issues

### 2.1 Content drift on 52 ELIs — decide canonical source
The drift list is not random; it clusters:

- **BR LAI pair:** `BR.L12527.*` (5 articles) and `BR.D7724.*` (9 articles) — likely a re-publication where the local .md reflects a newer consolidated text than what's in Qdrant.
- **BR Civil Code:** `BR.CC.PG.L1.T2.C2.Art.53–61` (9 articles) plus `Art.186`, `205`, `206.P3.V`, `927`, `932.III` — again looks like a whole-section refresh.
- **CL LPDC:** `CL.LPDC.Art.12, 23, 23bis, 50, 50A, 58` — note these *are* in Qdrant (unlike the sibling L19496/L20555 files), so the drift is textual, not existence.
- **ABEAR policies:** `PPE.Art.3`, `PAC.Art.3`, `PIAP.Art.3`, `PUC.Art.3` — all "Art.3". Suspicious pattern; could be a single template change propagated across documents.
- **Misc:** `CL.CPCL.C1.Art.269_ter`, `CL.DAN17.Art.11`, `INT.AN9.C6.S45.Art.6.45`.

**Action:** for each drift pair, pick a winner. My recommendation is to treat the local `.md` as canonical (it's what your editors control), re-embed from local, and record a `content_hash` on both sides so future drift is detectable at ingest time rather than audit time.

### 2.2 `doc_type_drift: 672`
This is the largest single quality number in the registry and is almost certainly a **derived-field mapping bug**, not 672 real mismatches. If downstream retrieval or filtering keys on `doc_type`, this could silently misroute hundreds of articles. Worth checking the mapping function before doing anything else, since fixing it may erase most of the drift.

### 2.3 PT/EN duplication of international treaties
Two related metrics:

- `alias_only_not_separately_ingested: 294`
- `colliding_elis: 293`

Reading the `INT/BR/*` vs `INT/EN/*` pairs: `INT/BR/ACHR_1969.md` and `INT/EN/ACHR_1969.md` publish the **same 30 ELIs**, and Qdrant keeps one copy. The Portuguese text is effectively **not retrievable as Portuguese** — only the English canonical. For a corpus with 55 PT files and 41 ES files, that's a significant loss for pt-query users.

**Options:**
1. **Language-suffix ELIs** (`INT.ACHR.PT.Art.1.1` vs `INT.ACHR.EN.Art.1.1`) — cleanest, but a breaking change.
2. **Keep one canonical ELI, store language as payload** and index *both* language variants as separate points keyed on `(eli, lang)`. Backwards-compatible; retrieval can filter on `lang`.
3. **Leave as-is** — only defensible if you truly never query in PT.

I'd recommend option 2 as the least disruptive.

- **`article_blocks_without_eli: 194`** is fully explained by the 3 `reference_only` files (157 + 18 + 19 = 194). These are correctly flagged. No fix needed.
- **`title_drift: 1`, `theme_drift: 1`, `tags_drift: 0`** — good hygiene. Locate the single title/theme offender and reconcile.
- **Language distribution is coherent:** PT=674, ES=179, EN=292 = 1,145. Nothing anomalous.
- **`duplicate_original_ids: {}`** — good; no Qdrant-side ID collisions.
- **`qdrant_articles_without_local_file: 0`** — good; no orphan points.

## 4. Recommended sequencing

1. **Fix `doc_type` mapping** first — cheap, may eliminate 672 warnings, and unblocks trustworthy filtering.
2. **Re-ingest the CL directory** (Section 1.1) to close the 26 missing ELIs and correct `source_basename`.
3. **Decide PT/EN treaty policy** (Section 2.3) and, if adopting option 2, migrate international-treaty points to `(eli, lang)` keys.
4. **Resolve 52 content-drift pairs** by re-embedding from canonical local `.md` and recording hashes.
5. **Re-run the registry generator** and require `validation_ok: true` before downstream indexing.

## 5. One structural suggestion

The registry currently mixes three concerns in one `files[]` array: *coverage* (local vs Qdrant), *identity* (alias / collision), and *content fidelity* (drift). For CI purposes, split the report into three sections with independent pass/fail gates, e.g. `coverage_report`, `identity_report`, `fidelity_report`. That way a PR that adds a new local file without re-ingesting (today's CL problem) fails a narrow, well-understood check rather than surfacing as a generic `validation_ok: false`.
