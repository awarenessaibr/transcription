# Law Registry v2 — Implementation Record for `04.1.md`

**Scope.** `04.1.md` was a specification in two parts: **Part A** a JSON Schema for
splitting the law registry into four independently-gated sub-reports, and **Part B**
a nine-section ingestion runbook. This document records **what was applied from
Part A**, **where the specification disagrees with the measured corpus**, and
**why Part B was not executed**.

**Verdict in one line.** Part A is implemented, tested and run against the live
collection; Part B's Phase A–E must not run until the four open decisions in §6 are
resolved, because three of its preconditions are already known to be unmet.

## 3. Where the specification disagrees with the corpus

### 3.1 Its own worked example is wrong

Part A's example asserts:

```json
{"collisions_total": 293, "intentional_multilocale": 293, "unintentional_duplicate": 0, "gate": "pass"}
```

The corpus has **4 same-language (`es`) collisions**, so `intentional_multilocale`
is 289 and the identity gate is **`fail`**:

| ELI | claimants | same-language |
|---|---|---|
| `CL.CPCL.C1.Art.228` | `CL/CL.CPCL.C1.Art.228.md`, `CL/CodigoPenal_Prevaricacion.md` | es |
| `CL.CPCL.C1.Art.229` | same pair | es |
| `CL.CPCL.C1.Art.269_bis` | `CL/CL.CPCL.C1.Art.269_bis.md`, `CL/CodigoPenal_269bis_269ter.md` | es |
| `CL.CPCL.C1.Art.269_ter` | **three** — adds `CL/CodigoPenal.md` | es |

`collisions_total: 293` in the example is correct; the other three values are not.
The rules and the example contradict each other, and **the rules were implemented**
(rule A.1.2: a same-language collision is an error, stop and report). Silently
matching the example would have set `unintentional_duplicate: 0` on a corpus that
has four.

### 3.2 Rule A.1.3 is a behavioural no-op today

`CANONICAL_LANGUAGE_PRECEDENCE = ("es", "en", "pt")` is implemented and tested, but
**all 289 multi-locale collisions are exactly `('en','pt')`**. For those, the rule
agrees with the parser's existing `_pick_variant(preferred_language="en")`. It is
correct as a rule and dead as a behaviour until an `es`/`en` pair appears.

### 3.3 The provenance gate cannot pass without changing the canonical writer

The gate requires `source_path` on every point. The live payload does not have it —
not on a sample, on **1119 of 1119 points**:

* payload keys actually present: `content, doc_type, metadata, original_data,
  original_id, source_file, tags, text, theme, title`
* `source_path` present on **0** points; `language` present on **0** points;
  `raw_sha256` / `norm_sha256` present on **0** points.

`LawArticle.to_payload(target="canonical")` writes `source_file` (a **basename**) and
only adds `source_path` under `include_extra`. The canonical shape is documented as
"shared with sibling projects and is therefore **additive only**", so making the
gate pass is a cross-project schema change, not a local fix. This is anti-pattern #2
in the specification; the specification correctly forbids it, and the corpus is
currently in violation of it.

## 4. v2 is not a superset of v1 — four consumers break

`law_registry.v2.json` omits fields that v1 published and that live code reads:

| Consumer | Reads |
|---|---|
| `templates/law-registry.html` | `summary.data_law_md_files`, `files[].articles_local / articles_in_qdrant / in_qdrant_eli / missing_eli / alias_eli / source_basename_present_in_qdrant` |
| `src/presentation/routers/law_registry.py` | returns `{summary, files, qdrant_only_articles, detail}` from the file |
| `README.md` (176–182), `ARCHITECTURE.md` (145) | both document the JSON as a **superset** of `discovery/case-server/pipeline/build_law_registry.js` |

v2 also **drops diagnostics v1 measured**: `doc_type_drift` (672), `title_drift` (1),
`theme_drift` (1), `tags_drift` (0), `duplicate_original_ids`, and the
`content_drift_eli` list. The four gates do not cover them. Because the schema sets
`additionalProperties: false` at every level, recovering them is a **schema
revision**, not an extra key — v2 is a *verdict* format, not a *diagnostic* format,
and the two must coexist until a v2.1 covers the gaps.

That is why `--output` defaults to `law_registry.v2.json`. Repointing it at the
tracked file is a migration, not a rename:

```bash
# only after the four consumers above are migrated
.venv-py312/bin/python scripts/build_law_registry_v2.py --output data/law/_mapping/law_registry.json
```

## 5. Cross-checks against v1

Independent agreement on every overlapping measurement:

| Measure | v1 | v2 |
|---|---|---|
| md files | `data_law_md_files` 119 | `summary.md_files_total` 119 |
| unique ELIs | `data_law_articles_unique` 1145 | `summary.elis_local_total` 1145 |
| points | `qdrant_points` 1119 | `summary.qdrant_points_total` 1119 |
| missing | `data_law_articles_not_in_qdrant` 26 | `coverage.missing_total` 26 |
| collisions | `colliding_elis` 293 | `identity.collisions_total` 293 |
| content exact / normalized / drift | 787 / 280 / 52 | `fidelity` 787 / 280 / 52 |
| language breakdown | `{pt:674, es:179, en:292}` | identical |

Two deliberate differences:

* **`missing` 26 vs 29.** v1's `files[].missing_eli` sums to **29** while its own
  `data_law_articles_not_in_qdrant` says **26**. Three missing ELIs
  (`228`, `229`, `269_bis`) are claimed by two files each, so the per-file lists
  double-count them. v2 counts unique ELIs in `coverage.missing_total` and keeps the
  per-file lists, so both readings are available from one document.
* **`validation_ok` lives in `detail`, not at top level.** The single boolean is
  `detail.validation_ok: false`; it is absent from the document root. v2 replaces it
  with `gates.overall`.

Note that v2's `fidelity` split is produced by a *different* normaliser than v1's
(`normalize_for_fidelity` additionally strips `> **BCN amendment note:**` blocks and
the trailing `---` authoring rule) yet lands on the identical 787/280/52. The two
normalisers agree on this corpus.

## 6. Findings that are new, and decisions they force

### 6.1 The Portuguese treaty text is not in the collection (new, verified)

For each of the 289 `en`/`pt` collision ELIs, the live text was compared against
**both** local variants:

| Live text equals | ELIs |
|---|---|
| English only | **280** |
| both (identical text in both languages) | 8 |
| neither | 1 |

So 280 of 289 ELIs have their Portuguese variant **absent from Qdrant**, and the
payload carries neither `language` nor a discriminating path (see 6.2), so nothing
in the collection records that these points are the English ones. v1 reports these
294 skipped variants as `alias_only_same_article_already_ingested` — a phrase that
reads as "nothing is lost". For the 280 it is inaccurate, and for the 4
same-language collisions it is wrong outright (those are duplicates, not aliases).

The odd one out is **`INT.AN9.C6.S45.Art.6.45`** — the same ELI v1 lists as content
drift, and the same one the parser notes as carrying a stray token. Two independent
measurements landing on one ELI.

### 6.2 A basename cannot identify a source (new, verified)

**21 of 98 distinct basenames are ambiguous** — every one an `INT/BR/*` vs
`INT/EN/*` treaty pair (`ACHR_1969.md`, `ICAO_Annex6.md`, `MC99_1999.md`,
`VCLT_1969.md`, … 21 pairs). The live payload stores
`source_file: "MC99_1999.md"` for a point whose actual source is
`INT/EN/MC99_1999.md`; `INT/BR/MC99_1999.md` produces the identical basename. The
only way to tell which language a point holds is to re-derive it from the corpus.

### 6.3 Decision: provenance

The gate is unsatisfiable against the current canonical shape (§3.3). Options:

1. Add `source_path` (+ `language`) to the canonical payload — additive, but a
   cross-project schema change that must be coordinated with the sibling projects.
2. Write the local `transcription_law` collection with the fields instead
   (`local_payload()` already has `source_path`), and scope the provenance gate to
   that collection.
3. Weaken the gate to accept `source_file` — **not recommended**: §6.2 shows it is
   lossy, and the specification's own anti-pattern #2 forbids it.

### 6.4 Decision: 04.md §2.3 option 2 vs specification A.1.3

`04.md` §2.3 recommends keying points by `(eli, lang)` so both treaty languages are
retrievable, calling the loss of PT text "a significant loss for pt-query users".
The specification's A.1.3 keeps **one** canonical point per ELI and records the
loser only as an `alternates[]` entry in the report. §6.1 shows the consequence of
A.1.3 as applied: 280 ELIs whose PT text is gone from the index. These two are
mutually exclusive and the choice is the user's.

### 6.5 Decision: `doc_type_drift` 672

`04.md` §2.2 flags this as likely a derived-mapping bug. The specification's A.2
makes fixing it a **precondition** to ingestion, so it is a Part B blocker. It is
unmeasured by the four v2 gates (§4).

### 6.6 Decision: Phase E is destructive

Phase E swaps the collection/alias on `la8159_law`, which is **shared with sibling
projects**. The specification's own precondition 1 requires a tested-restore backup
first. This must not be executed without explicit confirmation.

## 7. Part B status: not started, and why

Part B's preconditions are three of three unmet in the sense that matters: the
schema now exists (precondition 3 ✓), but

* **precondition 1** (backup + tested restore of a shared, cross-project collection)
  is an ops decision, not a code change;
* **Phase A.2** (`doc_type` mapping) is a known-failing precondition
  (`doc_type_drift: 672`);
* **Phase C** requires nine payload fields of which the live collection has five;
  writing the other four is the §6.3 decision.

Additionally, Part B's expected mutation counts (26–29 insert, 52 replace, 0 delete)
do not match the corpus: `extra_eli` is 0 and `duplicate_original_ids` is `{}`, so
there is nothing to delete, and the four missing-since-today ELIs (§3.1's
`228`/`229`/`269_bis`) make the insert count 26 unique, not 29.

Corpus baseline also moved during this work: **119 files / 1633 blocks / 293
collisions** (was 117 / 1631 / 292). `03.md`'s counts and its "clean against HEAD"
claim for `law_registry.json` are stale.

### Two deliberate departures from the specification

1. **A same-language collision fails the identity gate** (rule A.1.2) instead of
   being reported as `unintentional_duplicate: 0` (the example). `canonical_source`
   is left `null` for those, so the ambiguity cannot be mistaken for a resolution.
2. **`skipped` is a real gate state.** An offline run marks coverage, provenance and
   fidelity `skipped`, never zero — a zeroed `missing_total` reads as "checked and
   clean". `identity` is computed either way, so `--offline` still yields a verdict.

Both are documented in the module docstring, where the next reader will find them.
