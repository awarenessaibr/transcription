# Law Corpus Correction Report — `data/law`

Verification of `.dev/ongoing/02.md` ("Audit Report — `CPCL.txt` Findings")
against the **actual** `data/law` corpus, plus the defects that genuinely need
correcting.

## Method

All checks were **read-only**. Ground truth comes from the parser the project
actually ingests with, not from a re-implementation:

```
.venv-py312/bin/python scripts/ingest_law_corpus.py plan
```

and from `QdrantLawIndex.build_plan(default_law_dir())` called directly.

Parser output for the current corpus:

| metric | value |
|---|---|
| md files parsed | 117 |
| article blocks | 1631 |
| blocks without ELI label | 194 |
| articles with ELI | 1145 |
| **unique** ELIs | 1145 |
| collisions (same ELI, >1 file) | 292 |
| skipped language variants | 292 |
| articles actually ingested | 1145 |

Also used: `shasum -a 256 data/law/pdf/*.pdf`, `grep` over `data/law/**`,
`data/law/_mapping/law_registry.json`, and `data/law/json/**`.

### Independent verification of the parser (not a re-implementation)

"Ground truth is the parser" makes any parser bug self-confirming, so the P0
collision count was re-derived by a **second extraction that does not import
`qdrant_law_index` at all**. It walks `data/law/**/*.md`, splits on the level-3
heading, and matches a *generic ELI shape* — any backticked token with ≥3
dot-separated segments starting with an uppercase identifier — under two rules:

| pass | rule | files | blocks | duplicate ELIs |
|---|---|---|---|---|
| parser | `QdrantLawIndex.build_plan` | 117 | 1631 | 292 |
| **A** | generic shape, **only on lines mentioning an `ELI` label** | 117 | 1631 | 292 |
| **B** | generic shape, **any backticked token, anywhere** | 117 | 1631 | 292 |

All three agree exactly. Both passes split the 292 into **289** language aliases
and the **same 3** non-language collisions, and Pass B finds no duplicate that
Pass A misses — so no duplicate hides in an ELI-shaped token outside a labelled
line. The file/block totals also reproduce independently, as does the
194-block untagged set (157 + 18 + 19).

### A2. "Cached under the wrong statute" — not reproducible, and likely false

The report claims `CL.CPCL.Art.193/194/197/211` and `CL.CPR.Art.19.3` are "cached
in files such as `CHIPENCOD.md` or `Constitucion.md`, but those are **not this
article's statute**".

- `CL/CHIPENCOD_CP.md` is titled **"Codigo Penal Chileno"**, is sourced from
  `bcn.cl/leychile/navegar?idNorma=1984`, and its 12 ELIs are Código Penal
  articles: `CL.CHIPENCOD.T4.C3.Art.193/194/195/196/197`,
  `CL.CHIPENCOD.T4.C6.Art.211/212`, `T3.C1.Art.141`, `T3.C2.Art.148`,
  `T5.C2.Art.255`, `T6.C1.Art.296`, `T1.C1.Art.1`.
  Article 193 cached in a Código Penal file is cached under **exactly its own
  statute**. The claim is inverted.
- `CL/Constitucion.md` holds `CL.CONST.T1.C3.P2.Art.19.2` etc. — art. 19.x *is*
  constitutional. Correctly placed.

What **is** real, and is what the claim is groping toward: the same statute is
carried under **several namespaces**, so the same body of law looks like several
frameworks:

| statute | namespaces in use | where |
|---|---|---|
| Código Penal | `CL.CHIPENCOD.*` (12 arts) | `CL/CHIPENCOD_CP.md` |
| Código Penal | `CL.CodigoPenalChile.Art.*` (671 arts) | `data/law/json/CL/CodigoPenalChile/` — **json only, md has no ELIs** |
| Código Penal | `CL.CPCL.C1.*` / `CL.CPCL.T2.*` | `CL/CodigoPenal.md`, `CodigoPenal_Prevaricacion.md`, `CodigoPenal_269bis_269ter.md`, new `CL.CPCL.C1.Art.2xx.md` |
| Constitution | `CL.CONST.*` | `CL/Constitucion.md` |
| Constitution | `CL.CPR_BCN.*` | `CL/Constitucion_BCN.md` |
| Ley 19.496 | `CL.LPDC.*` (8 arts) | `CL/L19496_LPDC.md` (framework `LPDC`) |
| Ley 19.496 | `CL.L19496.Art.*` (11 arts) | 11 new `CL/CL.L19496.*.md` (framework `L19496`) |

Per-framework article counts in the index: `CPCL` 20 · `CONST` 17 ·
`CHIPENCOD` 12 · `L19496` 11 · `LPDC` 8 · `CPR_BCN` 4.

Arts. 193/194/197/211 therefore exist **twice** in the corpus's own terms —
`CL.CHIPENCOD.T4.C3.Art.193` and `CL.CodigoPenalChile.Art.193` (json). That
duplication, not a "wrong cache", is the defect worth fixing.

### A3. "No framework code yet" — false for the index, true only for the stale export

Framework codes are **derived from the ELI**, not from the metadata table
(`parse_file` → `split_eli(eli)`). Over all 1145 ingested articles:

doc_type distribution:  Code 207 · Resolution 181 · Law 164 · ICAO 157 · Internal 143
                        Decree 105 · Convention 104 · CDC 32 · Constitution 21
                        Contract 19 · Declaration 8 · Guidelines 4

So `CL.CPCL.C1.Art.228/229` → `CPCL`, `CL.LPDC.T1.Art.3.e` → `LPDC`. Nothing is
missing. The report's "no framework code" is an artifact of the **stale JSON
export**, which does carry `"doc_type": "unknown"` (e.g.
`data/law/json/CL/CodigoPenal_Prevaricacion.articles.json`, entry
`CL.CPCL.C1.Art.228`). The JSON layer was generated before `doc_type_for` learned
these codes; the md parser has since been fixed.

### A4. "Candidate not validated" — not a corpus property

There is no `established`/`candidate`/`status` field anywhere in `data/law`. The
only "status-like" key in the corpus is the registry's
`alias_only_same_article_already_ingested: 289`. This claim is entirely
bundle-side and has no counterpart to act on here.

### A5. Namespace inconsistency — partly real, but not the pairs named

- `CODIGOPENAL`: **zero occurrences** in `data/law/**` (case-sensitive).
- `CONSTITUCION`: **zero occurrences** in `data/law/**`.
- `CONST`: real (17 articles).
- `CPR`: real only as `CPR_BCN` (4 articles in `Constitucion_BCN.md`).

So "`CPCL` vs `CODIGOPENAL`" and "`CPR` vs `CONSTITUCION`" are bundle-side

  `CL.CodigoPenal_269bis_269ter.Art.269 ter`. **Confirmed real**, and it is the
  same defect as the 269_ter collision in Part B.

## Part B — Confirmed defects, ranked

### P0 — 3 real ELI collisions silently drop article text (introduced with the 16 new files)

The parser groups articles by ELI and, on collision, keeps the
`preferred_language` match else `variants[0]` (insertion order), recording the
loser as a "skipped variant". The 3 non-language collisions are:

| ELI | kept | **DROPPED** | block len (kept/dropped) |
|---|---|---|---|
| `CL.CPCL.C1.Art.228` | `CL/CL.CPCL.C1.Art.228.md` | `CL/CodigoPenal_Prevaricacion.md` | 937 / 745 |
| `CL.CPCL.C1.Art.229` | `CL/CL.CPCL.C1.Art.229.md` | `CL/CodigoPenal_Prevaricacion.md` | 727 / 749 |
| `CL.CPCL.C1.Art.269_ter` | `CL/CodigoPenal.md` | `CL/CodigoPenal_269bis_269ter.md` | 802 / 1116 |

**Comparison rule (stated, because this is a data-loss claim).** Four
normalisations were tried, in increasing strength, and **none** made any pair
equal: `raw`; `n_ws` = `re.sub(r"\s+", " ", s).strip()`; `n_md` = `n_ws` +
links→text + strip `* _ \``; `n_lower` = `n_md` + `casefold()`. For every pair
`n_md(kept) != n_md(dropped)` **and neither string is a substring of the other**,
so these are not formatting differences.

**But the three are not equally severe, and the earlier draft of this report
got that wrong.** Verified per block (BCN-note counts from `grep -c`):

- **`CL.CPCL.C1.Art.269_ter` — real content loss.** The kept
  `CL/CodigoPenal.md` block carries **0** BCN notes and is labelled
  `**Hierarchy:** Compat alias · Art. 269 ter` (the intent was an alias). The
  dropped `CL/CodigoPenal_269bis_269ter.md` block carries **3** BCN amendment
  notes — `LEY 20074 Art. 2 Nº4 b) D.O. 14.11.2005`, `LEY 19806 Art. 1 D.O.
  31.05.2002`, `Ley 21577 Art. 1 N° 8 D.O. 15.06.2023` — plus its own
  `**Theme:**` and a `**Source:**` BCN link (`bcn.cl/OOLWC1`). All of that is
  silently dropped on ingest.
- **`CL.CPCL.C1.Art.228` / `Art.229` — metadata divergence, not text loss.**
  Both files carry the *same* BCN notes (**2** and **1** respectively; file totals
  `CL.CPCL.C1.Art.228.md` 2, `CL.CPCL.C1.Art.229.md` 1,
  `CodigoPenal_Prevaricacion.md` 11 across its blocks). What differs is the
  `**Theme:**` — `Criminal Law – Public administration` in the kept new file vs
  `Criminal Law – Prevaricación` in the dropped pre-existing file — plus block
  ordering and a heading (`§ IV Prevaricación`). No statutory text or BCN note is
  lost here; the *classification* is.

**Worse:** all three are counted in the same
`alias_only_same_article_already_ingested: 289` bucket as the 289 benign
`INT/BR` × `INT/EN` language aliases, so the summary reports "292 skipped, all
aliases — fine" when 3 are conflicts — one of them destructive.

Fix:
1. Decide the canonical file per article, then remove the duplicate block from
   the other (`CodigoPenal_Prevaricacion.md` for 228/229;
   `CodigoPenal.md` for 269_ter — note `CodigoPenal.md` already labels it
   `**Hierarchy:** Compat alias · Art. 269 ter`, so the intent was to alias).
2. Make `build_plan` report **non-language** collisions separately from
   `skipped_variants`, and make them non-zero-exit-worthy. A collision between two
   Spanish-language files is a data bug; a `BR`×`EN` pair is not.

### P1 — `law_registry.json` is stale in both directions

- registry lists **100** files; disk has **117**
- registry references `CORP/SixthStreet_CodeOfEthics.md` — **not on disk**
- **18** on-disk files are unregistered, including all 16 new ELI-named files
  (`CL/CL.CPCL.C1.Art.228/229/256/257.md`, `CL/CL.L19496.*.md`,
  `CL/CL.L20555.Art.1.md`) plus `CL/CodigoPenal_269bis_269ter.md` and
  `CL/CodigoPenal_Prevaricacion.md` (the two collision losers)
- CL: **21 registered / 39 on disk**

**Diagnosis of the phantom entry.** `CORP/SixthStreet_CodeOfEthics.md` is not
invented — it was a real 420-line file that was **deleted from git in `3f84e30`
(2026-09-19 02:04)**, having been **committed in `6cf8fb8` (2026-09-18)**. The
registry's own `generated_at` is `2026-09-13T04:36:33` — *before* the commit that
added the file — so the entry predates the add and outlived the delete. Its
record is a structural clone of the LATAM one (`language=en`, `reference_only`,
`blocks_without_eli=19`, `articles_local=0`, same `reference_note`), which is why
it inflated `data_law_reference_only_files` to **4** where the parser now finds
**3**. This is a stale-entry problem, not a mystery file.

**Correction to the earlier draft:** `data/law/_mapping/` is **not untracked**.
It is tracked (`git ls-files data/law/_mapping` → 16 files) and
`law_registry.json` is **clean against HEAD**, so the staleness is *committed
state* and recovery/diffing is ordinary git:
`git show HEAD:data/law/_mapping/law_registry.json`. A `/tmp` copy
(`cp -a data/law/_mapping /tmp/law_mapping_backup`, 18 files,
`law_registry.json` sha256 `479a0d36ee880531…`) was taken anyway before any write
is contemplated.

**What the drift actually is:** the corpus on disk is *ahead* of git. The 16 new
ELI-named md files, the two collision losers' additions, 19 PDFs and 2 enrichment
files are all **untracked** (`git status` → `??`), while the registry that
describes the older 100-file state is **committed**. So regenerating the registry
is only half the fix; the new files must be committed too, or the next clean
checkout will reproduce exactly this drift.

Fix: `python scripts/ingest_law_corpus.py validate --write-registry`, then commit
the untracked corpus additions alongside it.

### P3 — PDF provenance gaps in `data/law/pdf/` (19 files on disk)

Re-derived by extracting every `sha256sum <name>.pdf` placeholder and every

- **Version-control gap (new):** all 19 on-disk PDFs are **untracked**, and the

### P3 — `data/law/json/` is a stale second ID scheme

- produced by `scripts/markdown_law_to_json.py`, **consumed by nothing in `src/`**
- CL coverage 23 docs vs 39 md files; no entry for the 16 new files
- it **synthesises** stem-based IDs for md files that have no ELI blocks

not authoritative" marker.

### P3 — Metadata header format split

Two mutually exclusive header formats: **28** files use a Markdown table
(`| **Source URL** | … |`), **87** use a bullet list (`- **Source:** …`),
**2** use neither. Any tool that parses one form silently sees no metadata for
the other 87 or 28.
